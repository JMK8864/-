## 2. 전체 S/W 구조

```
 [현장 도크 PC / PLC 게이트웨이]                       [운영자 브라우저]
   tcplinent.emul.console.ftms (콘솔 에뮬, 60 도크)            │ http :80
   tcpclient.emul.ftms (WPF 에뮬)                              ▼
        │ TCP 6004~6006                         ┌────────────────────────────────┐
        │ STX(0x02) JSON ETX(0x03)              │ 리버스 프록시                    │
        ▼                                       │  nginx(WSL Docker) 또는 YARP     │
 ┌───────────────────────────────────────────┐  └──┬───────────────┬─────────────┘
 │           app-server.ftms  (:8121)        │◄───┘ /api /chathub  │ 그 외 전부
 │ TcpServerFinalService ─► ITcpMessageHandler│      /health        ▼
 │      │ process_count          │ heartbeat │      ┌─────────────────────────────┐
 │      ▼                        ▼           │      │ :8122                        │
 │ DataCollectorService   LogisticsSystem-   │      │ 개발: DxfBlazorViewer 개발서버 │
 │  ├ collected_payload     StateManager     │      │ 운영: web-server.ftms(정적)   │
 │  ├ PG 함수 집계          └ EventDataStore- │      └─────────────────────────────┘
 │  └ 5분 누적(메모리)        Service         │        ▲ 배포되는 SPA
 │ REST Controllers · SignalR ChatHub        │        DxfBlazorViewer.Client (현행)
 │ Identity + JWT(Access) + Refresh 쿠키      │        wasm-scada.ftms (구버전)
 └───────────────────┬───────────────────────┘
                     ▼
     PostgreSQL 17 + TimescaleDB : authdb / ftmsdb
```

### 2.1 핵심 데이터 흐름

1. **Heartbeat**: 도크 → `{"type":"heartbeat", DeviceStatuses...}` → `JsonMessagedHandler` → `LogisticsSystemStateManager.GetResponseHeartbeatMessageAsync`
   - 장치 상태 정규화 후 `EventDataStoreService` 에 저장(메모리 + 10초 주기 DB flush)
   - 응답에 해당 도크의 **현재 분류(Sorting) 파라미터**를 실어 보냄 → 서버가 설정을 "푸시"하는 구조
   - `DeviceStatusManager` 가 상태 비트 변화를 알람(`ftms_event_log`)으로 기록
2. **ProcessCount(처리수량)**: 도크 → `type:process_count` → `DataCollectorChannel` → `DataCollectorService`
   - 10개 회전 큐 → 1초/2만건마다 CSV 텍스트로 `collected_payload` 적재
   - `process_collected_payload_v4()` → `process_counts` / `rawdata_table`
   - `process_counts_aggregate_all()` 1초 주기 → 분/시/일 누적 테이블
   - 최근 N분(기본 5분, DEBUG 1분) 슬라이딩 누적을 메모리에 유지, SignalR `CollectedCountReceived` 푸시
3. **설정 변경**: 웹 → `POST /api/setting` → DB 저장 + `AssetItemUpdateChannel` → StateManager 메모리 반영 → 다음 Heartbeat 응답으로 도크에 전달
4. **UI**: Blazor WASM 이 REST(`/api/...`, **상대 주소**)로 조회·폴링, SignalR(`/chathub`)로 실시간 수신, DXF 도면(`/api/dxf`, MessagePack+LZ4)을 SkiaSharp 로 렌더링
   → 화면과 API 가 **같은 주소(오리진)** 여야 하므로 리버스 프록시가 필수

## 5. 데이터베이스 구조 (테스트로 확인)

### 5.1 누가 무엇을 만드는가
| 생성 주체 | 대상 |
|---|---|
| 수동 (가이드 7단계) | 계정 `tapsuser`, DB `authdb`·`ftmsdb`, 확장 `timescaledb`·`pgcrypto` |
| app-server `EnsureCreated` (8단계, 첫 실행) | authdb: ASP.NET Identity 테이블(`asp_net_users` 등) + 시드 계정 7개 / ftmsdb: `settings`, `process_counts`, `scan_data`, `ftms_event_list` 등 EF 모델 테이블 |
| app-server 기동 시 SQL (`CollectedPayloadRepository`, `DataDbInitializer`) | `collected_payload`·`rawdata_table` 하이퍼테이블, 함수 `process_collected_payload_v4()` |
| 수동 스크립트 (9단계, `setup/db/03_*.sql`) | `ftms_event_log`·`dock_message_events` 하이퍼테이블(90일 보존), `process_counts` 하이퍼테이블 변환 + `is_aggregated`, 분/시/일/일(KST) 누적 하이퍼테이블 4개, 함수 `process_counts_aggregate_all()`, `get_dock_process_statistics_lastest()` |

### 5.2 결과 (검증 환경)
- 하이퍼테이블 **9개**: `collected_payload, dock_message_events, ftms_event_log, process_count_per_day_accum, process_count_per_day_kst, process_count_per_hour_accum, process_count_per_minute_accum, process_counts, rawdata_table`
- 함수 **3개**: `get_dock_process_statistics_lastest, process_collected_payload_v4, process_counts_aggregate_all`

### 5.3 주의
- `EnsureCreated` 는 DB 에 테이블이 **하나라도 있으면 아무것도 만들지 않음** → 반드시 빈 ftmsdb 로 첫 실행 후 9단계
- 원본 `Database/0-0 …sql` 에는 주석 처리 안 된 `delete from process_counts; …` 가 있어 **통째로 실행 금지** (가이드의 `03_*.sql` 은 제거본)
- `Database/procedure` 폴더는 구버전(집계·통계 함수, 하이퍼테이블 없음) — 사용하지 않음
- 원본 `1-1 …계정 생성.sql` 은 BOM 포함, 스키마 GRANT 가 접속 중인 DB 에만 적용, `CREATE EXTENSION timescaledb` 없음
- 스키마 정의가 EF 모델 / 앱 내장 SQL / `Database/*.sql` 세 곳에 분산, Migrations 미사용 → 스키마 변경이 기존 DB 에 반영되지 않음

## 6. 기술적 특징 (잘 된 점)

- **System.IO.Pipelines** TCP 수신 + STX/ETX 프레이밍 — 부분/연속 패킷 처리 정확
- **핸들러 플러그인 구조**(`ITcpMessageHandler` 리플렉션 자동 등록, Priority)
- **Minimal API 커맨드 패턴**(`IApiCommand` 구현만 추가하면 엔드포인트 생성)
- **고속 수집 경로**: 회전 큐 → 배치 → PL/pgSQL 집계, TimescaleDB 분/시/일 누적 — 60 도크·초당 100건에서 `pending` 이 작게 유지됨(테스트)
- **DXF 전송 최적화**: MessagePack + LZ4, Accept 헤더로 형식 선택
- **권한 모델**: Role 7단계 × Permission 비트플래그 → Policy 자동 생성
- **운영 편의**: Serilog 롤링, 런타임 로그레벨 변경 API, `/health` 에 외부 연결 상태
- 리버스 프록시 경로가 단순(`/api`, `/chathub`, `/health`, 나머지) → **nginx 로 1:1 대체 가능**(테스트 검증)

## 9. 권장 조치 우선순위

1. **즉시(보안)**: register 제거 또는 `[Authorize(Policy=CanManageUsers)]` + 기본 Role=Viewer / 전역 `AuthorizeFilter` 후 필요한 곳만 `[AllowAnonymous]` (이때 WASM HttpClient 에 토큰 자동 첨부 핸들러 추가 필수 — 부록 REST API §5) / 시드 계정 제거·최초 비밀번호 변경 강제 / Secret·DB 비밀번호를 환경변수·User Secrets 로 이동하고 **키 교체** / CORS 화이트리스트 / 토큰·연결 문자열 로그 출력 제거
2. **단기(안정성)**: B1(타이머 예외), B2(Flush 유실), B3(Default 객체 오염), B6(집계 루프 정지), B12(DB 연결 재시도), B15(테이블 불일치) — 대부분 수 줄 수정
3. **중기(빌드·구성)**: NuGet 버전 고정(Central Package Management), 공용 어셈블리 참조 방식 통일, `global.json` 활성화, EF Migrations 도입·스키마 정의 일원화, 에뮬레이터 하트비트 즉시 시작(B16)
4. **장기(구조)**: 죽은 코드 정리, 대형 파일 분리, 빈 catch 제거·로깅 일원화, 핵심 파이프라인 단위 테스트, 폴링 → SignalR 푸시 전환
